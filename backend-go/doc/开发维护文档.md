# Artifex 后端开发维护文档

Artifex 是一个本地图集管理工具。本文的「图集」对应前端所说的「插画组」，多个图集组成一个图库，`database_dir` 指向该图库的根目录。Go 进程提供 HTTP API，可同时托管 React 单页应用，也可在终端显示启动状态和日志。SQLite 保存图集、插画、标签索引和图集级偏好，原图、缩略图和可选的 ONNX 模型存放在库目录。上传可直接读取图像内嵌的 ComfyUI 生成参数，也可用本地模型生成检索标签。前端交接见[前端开发维护文档](../../frontend/doc/开发维护文档.md)。

## 1. 本地启动

主 Go 模块在 `backend-go/`，[go.mod](../go.mod) 声明 Go **1.26.4**。构建主程序和包含 `tagger` 的包需要启用 CGO，并配备目标平台对应的 C 编译器（Windows 可用 MinGW-w64，Linux/macOS 用本机 GCC 或 Clang）。SQLite 使用 `modernc.org/sqlite`。前端构建可使用发布流程采用的 Node.js 20 和 npm。

在仓库根目录用 PowerShell 执行下列命令。它将可执行文件和配置放在一个新的临时目录，首次联调会创建独立的空图集库。

```powershell
Push-Location frontend
npm ci
npm run build
Pop-Location

$frontendDist = (Resolve-Path 'frontend/build').Path
$runDir = Join-Path ([System.IO.Path]::GetTempPath()) ("artifex-dev-" + [guid]::NewGuid().ToString("N"))
New-Item -ItemType Directory -Path $runDir | Out-Null
$artifexExe = Join-Path $runDir 'artifex.exe'
$env:CGO_ENABLED = '1'

Push-Location backend-go
go build -o $artifexExe .
Pop-Location

[System.IO.File]::WriteAllText((Join-Path $runDir 'config.toml'), "auto_tag = false`n")
& $artifexExe -no-ui -frontend $frontendDist
```

打开终端输出的实际 URL。默认从 `127.0.0.1:8000` 开始，只在端口已被占用时尝试下一个端口，默认共尝试 30 次。`-port 0` 可由系统分配空闲端口。开发前端热更新时可另开终端，以 `http://localhost:3000` 启动 CRA，并将 `REACT_APP_API_BASE_URL` 设为后端实际 URL。该变量在前端启动或构建时读取。打包联调使用上面的同源方式。

- `-no-ui` 或输入输出缺少交互终端时，后端直接向标准输出记录日志。交互模式提供 `/open`、`/log`、`/status`、`/help`、`/quit`，`-cli-theme` 可覆盖当前进程的终端主题。
- 后端以**可执行文件所在目录**为默认基准，读取同目录的 `config.toml`。未设置 `database_dir` 时，也在该目录初始化图集库。直接 `go run .` 时可执行文件位于 Go 临时目录。希望重启后复用测试库时，构建到一个固定目录。
- 默认的静态资源探测依次看可执行文件旁的 `_internal/frontend`、`frontend`，并尝试上一级的 `frontend/frontend`。CRA 当前产物是 `frontend/build`，开发时用 `-frontend` 指向含 `index.html` 的目录。缺少页面资源时仍可联调 `/api/*`。
- 本地 API 无身份验证，默认只监听本机。图片、模型、配置修改均由同一个进程提供。当前开发 CORS 放行 `localhost:3000`、`localhost:5173` 和 `127.0.0.1:5173` 的 HTTP 源。

入口和环境配置分别在 [main.go](../main.go)、[settings.go](../internal/settings/settings.go) 与[前端 URL 处理](../../frontend/src/api/url.js)。

## 2. 代码地图

主进程的调用顺序是 `run → appRuntime.bootstrap → server.NewServer → http.Server.Serve`。启动先读设置和尝试加载标签模型，再打开数据库、挂载路由并绑定端口。模型不可用会记告警，图集 API 仍可运行。交互和无界面模式共用这一启动路径，退出时先等待 HTTP 关停，再卸载标签会话和关闭 SQLite。

| 区域 | 入口与职责 |
| --- | --- |
| 进程与终端 | [main.go](../main.go) 处理参数、端口、启动和退出。[`internal/cli`](../internal/cli) 用 Bubble Tea v2 的 `Init/Update/View` 管理首页、日志页、主题与命令。[`internal/applog`](../internal/applog/log.go) 保留最近日志、生成快照，并在无界面模式镜像到标准输出。 |
| API 与传输 | [server.go](../internal/server/server.go) 注册 Chi 路由、恢复中间件、日志、CORS、图集锁和静态页面回退。[models.go](../internal/models/models.go) 定义大部分请求和响应结构。具体处理器按业务分文件。 |
| 数据与设置 | [database.go](../internal/database/database.go) 初始化 SQLite 表、FTS5 和触发器。[settings](../internal/settings/settings.go) 读写全局 TOML。[groupconfig](../internal/groupconfig) 负责图集视图、排序和颜色操作的验证与事务。 |
| 图像流水线 | [illustrations.go](../internal/server/illustrations.go) 负责上传、读写、标签和详情刷新。[thumbnail](../internal/thumbnail/thumbnail.go) 保持纵横比生成 JPEG。[workerlimit](../internal/workerlimit) 提供可调整的并发槽和按权重计费的解码预算。 |
| 生成参数与模型 | [metadata](../internal/metadata) 解包 PNG/WebP 和解析 ComfyUI 节点图。[tagger](../internal/tagger) 管理默认模型、CSV 标签和 ONNX Runtime 会话。[model.go](../internal/server/model.go) 提供模型 HTTP 接口。 |
| 批量导出 | [export.go](../internal/server/export.go) 提供候选清单、草稿、一次性凭证与 ZIP 流。候选筛选、文件路径展开和预览树在前端计算。 |

## 3. 数据归属与切换

```text
可执行文件目录/
  artifex[.exe]
  config.toml
  frontend/index.html             # 发布包静态入口
  onnxruntime.dll 或平台对应的共享库

database_dir/                    # 缺省与可执行文件目录相同
  gallery.db                     # SQLite，运行时可出现 -wal 和 -shm
  uploads/<groupId>/
    originals/<illustrationId>_<原文件名>
    thumbnails/<同名文件>
    thumbnails_normal/<同名文件>
  models/
    default/
    user_model/
```

- **全局 TOML** 保存 `database_dir`、自动标签开关、GPU 和活动模型、上传冲突策略与并发、白板渲染器和自由分组行限制、下载命名格式、`[cli]` 主题与端口尝试次数。常用默认值为 `auto_tag = true`、`upload_conflict_policy = "save_all"`、`upload_workers = 4`、`tagger_slots = 1`、`board_renderer = "auto"`、`board_free_row_limit = 10`。配置中的库目录须为绝对路径，Windows 可用 TOML 单引号包住反斜杠路径。CLI 和 HTTP 设置写入共用 `settings.Update`，在进程内串行读取、合并和验证，以同目录临时文件同步后替换配置。CLI 的 `/port-attempts` 重启生效，`/upload-workers` 和 `/tagger-slots` 更新后应用于新任务。已取得槽位的任务继续运行，调限期间旧槽和新槽可同时占用。
- **库内 SQLite** 使用 WAL、外键和 5000 ms `busy_timeout`。`groups` 代表图集，`illustrations.group_id` 关联归属图集。`group_configs` 用 JSON 列存每个图集的 `view` 与 `colors`，`group_order` 保存显式图集顺序，`export_drafts` 用 JSON 保存全库或单图集的导出草稿。删除图集会级联删除该图集的插画、视图、排序和单图集草稿。封面 ID 由处理器维护，插画删除或覆盖时清除旧封面引用。`illustrations_fts` 只索引 `tags`，通过主表增删改触发器同步。
- **库切换** 由 `PUT /api/settings` 处理。所有 API 进入 `withLibrary`，普通请求持读锁，设置更新持写锁。切换会等待正在执行的上传、模型请求与文件流结束，验证并打开目标库，保存设置，再换连接、目录和身份标识。切换指向已有库或初始化一个新库。要搬迁数据，停服后复制库文件与目录，再调整设置。
- **库身份** 通过 `X-Artifex-Library` 响应头暴露，每次启动和切库都会生成新值。请求携带旧身份时返回 `409`。前端 [fetchLibrary](../../frontend/src/api/library.js) 在页面生命周期固定首次读到的值，切换设置后刷新页面。API 响应设为 `no-store`，后端还移除条件缓存头，避免新库复用旧库同 ID 的图片。直接图片 URL 一般由浏览器加载，JSON 请求按身份头保护，ZIP 下载则由凭证绑定到同一库。
- **备份与旧版** 停止进程后，按目录备份 `gallery.db`、`uploads/`、可选的 `models/` 以及独立的 `config.toml`。活跃 WAL 库应通过 SQLite 一致性备份能力获取数据库快照，单独复制正在使用的主文件可能漏掉 WAL 中的写入。当前建表只使用 `IF NOT EXISTS`。历史提交 `dec72a4` 曾使用 `groupconfig.json`，`f0538c9` 将图集偏好迁到 SQLite。维护旧库时先备份并验证实际结构，当前读取路径以 SQLite 为准，仓库没有自动导入旧 JSON 的流程。

## 4. API 索引

下表路径均以 `/api` 为前缀，路由以 [server.go](../internal/server/server.go) 为准。大多数失败返回 `{"detail":"..."}`，前端 [request 封装](../../frontend/src/api/index.js) 读取该消息并将 `204` 当作无响应体。文件响应和归档响应是二进制。

| 方法与路径 | 用途与要点 |
| --- | --- |
| `GET /groups` · `POST /groups` | 列出图集及封面和插画计数，或提交 `{name}` 创建图集（201）。 |
| `GET /statistics` | 读取当前馆藏总量、磁盘占用分项和各图集的逐日导入计数。口径见第 10 节。 |
| `GET /statistics/groups/{groupId}/storage` | 读取图集内各插画对应文件的磁盘占用，供颜色组汇总使用。 |
| `GET/PUT/DELETE /groups/{groupId}` | 读取、重命名、设置封面或删除图集。封面插画必须属于该图集。重命名和设置封面宜分开提交，当前处理器先更新名称再校验封面。删除成功为 204，上传目录在返回后异步清理。 |
| `GET /groups/{groupId}/illustrations` | 插画页 `{items,total,offset,limit}`。新入库和未手动排序的插画按创建时间和 ID 倒序显示，已排序插画按保存的位置排列。默认 `offset=0`、`limit=50`，`limit` 最多 100000。 |
| `POST /groups/{groupId}/illustrations/upload` | multipart，字段 `files` 可重复。可选 `skip_auto_tag=true` 与 `conflict_policy`，201 含四组逐项结果。 |
| `POST /groups/{groupId}/illustrations/reorder` | 批量移动插画至指定锚点前后，支持同时修改活动方案中的手动归属。返回更新后的图集配置快照。 |
| `GET/PUT/DELETE /illustrations/{illustrationId}` | 读取详情、写入单图 `tags`、删除单图。当前无跨图集移动接口。 |
| `GET /illustrations/{illustrationId}/file` · `/thumbnail` · `/metadata` | 原文件（可用 `download=true`）、缩略图（`quality=low\|normal\|original`）、生成参数详情与按需刷新。 |
| `POST /illustrations/tags` · `POST /illustrations/retag` | `{ids,operation,tags}` 批量追加或移除标签，操作为 `add` 或 `remove`，响应为 `updated/missing`。`{ids}` 重新推理会替换整列标签，响应为 `updated/failed`。模型未加载时重打标签返回 503。 |
| `GET /search` · `GET /tags` · `GET /prompts` | `q` 经逗号与空白分词，再组成 FTS5 的 AND 前缀查询，按 rank 排序，`limit` 最多 200。`tags` 汇总标签建议，`prompts` 从已有扩展数据的正/负提示词中分词、去重并排序。 |
| `GET/PUT /settings` | 全局配置。PUT 只合并提供的设置字段，可切库或更新模型和并发，响应返回当前设置。终端 `cli` 子段由 CLI/TOML 维护。 |
| `GET/PUT /group-config` · `POST /groups/{groupId}/color-operations` | 图集配置快照、部分视图/排序更新、颜色事务，详见下节。 |
| `GET /model/status` · `POST /model/download` · `DELETE /model/default` | 默认模型缓存和当前会话状态，拉取并尝试加载默认模型，或删除默认模型缓存。 |
| `GET /models` · `POST /models/upload` · `DELETE /models/{modelName}` | 列出默认/自定义模型与活动模型，上传 `file`（ONNX 或 CSV），按文件名删除自定义文件。上传同名返回 409。 |
| `GET /export/catalog` · `GET/PUT /export/draft/{scope}` · `POST /export/download` · `GET /export/download/{ticket}` | 批量导出候选、持久化草稿、准备下载、取得 ZIP，详见第 7 节。 |

## 5. 上传、检索与删除

1. [UploadIllustrations](../internal/server/illustrations.go) 先确认图集存在、解析 multipart 并加载设置。单文件上限 2 GiB，整个请求上限 2 GiB 加 1 MiB，32 MiB 是 multipart 内存阈值，超出阈值的数据可落临时文件。开启自动标签且请求未跳过、但模型不可用时返回 409，可用 `skip_auto_tag=true` 重试。
2. `prepareUploads` 并行准备，每张图在图集目录的 `.upload-*` 中暂存。通过全局上传槽控制任务数，先读尺寸并限制到 1 亿像素，再用 512 MiB 的共享**估算**预算约束解码与缩放阶段。按实际内容解码 JPEG、PNG、GIF 或 WebP，写回宽高和 MIME。生成最长边约束为 400 和 1200 的两档 JPEG（质量 75 和 85），保持比例，缩略图磁盘名沿用原文件的后缀，HTTP 类型为 `image/jpeg`。
3. `commitPreparedUpload` 逐文件按请求顺序提交，并用 `uploadCommitMu` 将并发请求的文件搬运和冲突判断串行化。先在事务中拿到插画 ID，再把原图和缩略图移到正式位置，写入大小、尺寸、MIME、标签和扩展数据。失败时回滚并清理已移入文件和暂存目录。SQLite 提交与文件系统变更分属两个系统，异常退出后排查应同时核对目录与数据库。
4. 冲突按**同图集同原文件名**判断。`save_all` 新增独立 ID，`skip` 跳过，`overwrite` 新建 ID 并删除查到的一条旧记录，清掉旧封面引用，提交成功后移除旧文件。`added` 含新增插画对象，`skipped`、`overwritten`、`failed` 含文件名等结果。收到 201 后仍需检查 `failed`。覆盖成功后重新获取列表来拿新 ID。

原图和缩略图通过 DB 记录定位。缩略图缺失时尝试从原图重建。单图删除先事务清除封面和主记录，再尽力删除三份磁盘文件。批量标签操作在一个事务里增删、按大小写不敏感方式去重，重新打标签逐张处理并报告失败，FTS 同步由触发器负责。手动颜色分配存的是 JSON 内的插画 ID。前端删除流程尽力调用 `clear_assignments`，直接调用删除 API、覆盖旧图或清理失败时可能留下旧分配。

## 6. 图集配置与颜色操作

区分 **图集**（`groups` 表、整数 `group_id`）、**颜色方案**（`colors.sets` 的 set、字符串 ID）和**颜色分组**（方案中的 pair、字符串 ID）。后端持久化规则和手动归属，实际自动匹配在浏览器执行。

- `GET /group-config` 从一致快照读取 `{group_order: [], groups: {}}` 形状，`groups` 以十进制图集 ID 为键，只含已保存的配置。缺失视图使用 `DefaultView`，例如默认降序、低清、卡片尺寸 3、每页 50、颜色分组单列、全量预览。读旧视图会先载入默认值再合并存量字段，结构无效时回退。缺失或无效的颜色 JSON 读取为空方案集。
- `PUT /group-config` 支持如 `{"groups":{"1":{"view":{"quality":"normal"}}}}` 的字段级补丁。带 `group_order` 时该数组整项替换，可以为空，已有图集 ID 必须为正且不重复。颜色的读和写分开，`colors` 出现在通用写入体会被拒绝。
- `POST /groups/{groupId}/color-operations` 接收 `{"operations":[...]}`。可用操作有 `create_set`、`update_set`、`delete_set`、`set_active`、`create_pair`、`update_pair`、`delete_pair`、`reorder_pairs`、`reorder_rules`、`assign`、`clear_assignments`。显示顺序是 `pairs`，自动匹配优先级是 `match_order`。排序按提交的现存 ID 重新排列，未提交的现存项按原顺序追加。修改单个 pair 只写 `changes` 提供的字段，删除 pair 同时清掉该规则的顺序项和手动分配。
- 颜色结构是 `{sets,active_id}`，每个 set 有 `id,name,pairs,match_order,manual_assignments`。pair 字段为 `id,customName,terms,color,borderColor`。规则项要提交 `value,scope,operator,negated,open,close`，作用域为 `all/tag/prompt`，逻辑操作为 `and/or`，括号须配平。新增手动分配时确认插画属于当前图集。`manual_assignments` 的空字符串表示手动设为未归组。`assign` 的映射值为 `null` 时清除手动覆盖、恢复自动匹配，`clear_assignments` 可按插画 ID 清理整个图集各方案中的分配。
- 插画排序接收 `{"ids":[5,3],"anchor_id":7,"side":"before"}`，移动批次严格按 `ids` 顺序插入。可选的 `color: {"set_id":"…","assignments":{"5":"…","3":null}}` 只修改批次内明确列出的归属。此接口的 `null` 表示移到未归组。两项变更在同一事务内保存。活动方案已切换，或锚点、移动项已经失效时返回 409。排序保存在 `illustration_order` 表，旧库自动建表，删除和覆盖会级联清理旧位置。
- 这些写操作都经 [store.go](../internal/groupconfig/store.go) 的 `BEGIN IMMEDIATE`，先预留写事务，再读取当前已提交值，依次验证、合并并提交。视图 upsert 只覆盖 `view`，颜色 upsert 只覆盖 `colors`。任意一步失败会回滚整批。格式不合法返回 400，图集或必需的颜色对象不存在返回 404，重复创建返回 409（`create_set` 可用 `if_absent` 进行幂等创建）。

契约入口为 [groupconfig.go](../internal/server/groupconfig.go)、[视图定义](../internal/groupconfig/groupconfig.go)、[颜色结构](../internal/groupconfig/colors.go) 和[操作实现](../internal/groupconfig/operations.go)。

## 7. 批量 ZIP 导出

[export.go](../internal/server/export.go) 将导出拆成清单和草稿、准备请求、浏览器下载三个阶段。

1. `GET /export/catalog?scope=all` 列全库候选，也可传正整数图集 ID。响应按 ID 倒序，含文件名、尺寸、大小、标签等筛选所需字段，扩展数据只附带已存的正/负提示词。前端用这些数据预览文件名、文件夹和导出范围。
2. `GET /export/draft/{scope}` 读取草稿，缺省返回 JSON `null`。`PUT` 接收至多 4 MiB 的 JSON 对象，成功返回 204。全库 `all` 在 SQLite 中存为 `scope=0`，单图集以自身 ID 为 scope，后者随图集删除。草稿为前端拥有的配置结构，写入方式为整份替换。
3. `POST /export/download` 接收最多 32 MiB 的 JSON 数组 `[{id,path}]`。后端验证正整数且唯一的插画 ID、归档路径（正斜杠、组件长度、控制字符、保留设备名、路径穿越）和忽略大小写的文件/目录冲突，再按 ID 查询库内原图。文件缺失返回 409，成功返回 `{url}`。待领取凭证最多 8 个，超限返回 429。
4. `GET /export/download/{ticket}` 领取凭证并以 `zip.Store` 逐项流式写出原图字节。凭证保存在进程内、绑定库身份、2 分钟有效且只能领取一次。失败重试需重新准备。准备到下载之间原图若被覆盖或删除，已准备的归档仍可能中断。

## 8. ComfyUI 元数据与自动标签

**生成参数**从[容器解析](../internal/metadata/webp.go)开始，按签名识别 PNG 或 WebP。PNG 校验 CRC 并解析 `tEXt/zTXt/iTXt`，[PNG 读取器](../internal/metadata/png.go)限制文字数量和解压大小。WebP 读取 RIFF 的 EXIF/TIFF 中带 `prompt:` 或 `workflow:` 前缀的值。损坏或无支持元数据的图像仍可上传，至少保存文件信息与解析器版本。

[extract.go](../internal/metadata/extract.go) 优先读取执行时的 prompt 图，workflow 只补同 ID 同类型节点缺失的输入。没有 prompt 图时使用 workflow。[graph.go](../internal/metadata/graph.go) 展开子图、兼容节点连接格式与绕过节点，并限制深度和节点数。[registry.go](../internal/metadata/registry.go) 记录已知节点的 widget 顺序。[resolve.go](../internal/metadata/resolve.go) 从保存/预览输出回溯独立的采样阶段，沿语义连接解析模型、提示词和 LoRA。[schedule.go](../internal/metadata/schedule.go) 解析已知的 sigma 变换。第一阶段映射到旧的顶层显示字段，`Generation Stages` 保留多阶段信息，种子通过 `json.Number` 读取并转换成字符串，以保留 64 位整数精度。

旧图在打开 `/metadata` 时，根据 `parser_version` 按需重新抽取。处理器只用数据库记录定位库内原图，检查相对路径和符号链接，只解码图像尺寸，用比较并交换的写入条件避免覆盖并发改动，原图不可读时保留历史结果。修改解析规则时检查顶层展示字段、`Generation Stages`、提示词建议和导出清单，并按需更新 `ParserVersion`。列表和导出清单读取的是存量 DB 数据，单独浏览列表不会逐图触发升级。

**自动标签**由 [tagger.go](../internal/tagger/tagger.go) 在本地运行。标签模型输入为 `input`（`float32`、NCHW、`1×3×448×448`），输出 `output` 按 CSV 行顺序解释。图像预处理含缩放和 ImageNet 归一化，输出经 sigmoid 后，普通标签（category 0）阈值为 0.35，角色标签（category 4）为 0.75。共享会话用读写锁保护，多次推理由 `tagger_slots` 控制，会话切换等待运行中的推理完成。CUDA 提供程序无法启用时记录告警并尝试 CPU。

- 默认模型由 [tagger/model.go](../internal/tagger/model.go) 固定 Hugging Face revision、三个文件的字节数和 SHA-256。下载先落独立暂存目录，整套校验成功后换入 `models/default/`。默认模型加载会校验摘要，列表缓存状态仅校验文件大小。状态接口的 `cached` 同时要求默认模型缓存存在且当前推理会话已就绪。
- 自定义模型存放于 `models/user_model/`。CSV 选择顺序是同名 `<stem>.csv`、用户目录 `tags.csv`、默认模型 `tags.csv`。CSV 需含 `name`，输出分类依赖 `category`。上传文件后，通过 `active_model` 选择 ONNX 文件，空值表示默认模型。
- ONNX Runtime 优先从可执行文件同目录找 `onnxruntime.dll`、`libonnxruntime.so` 或 `libonnxruntime.dylib`，找不到时交由系统加载路径。标签失败时先看 `/log` 或标准输出里的 `model`、`tagger`。确认配置指向正确的库、模型文件及 CSV 齐全、共享库版本匹配、推理输入输出形状兼容。缺少运行库或模型时仍可关闭自动标签来验证其余业务。

## 9. 修改与验证

在 `backend-go/` 运行 `go test ./...` 检查主模块能否编译。当前主模块没有随仓的 Go 测试，业务回归可按下表验证。历史提交 `82fe1df` 的 `backend-go/internal/groupconfig/store_test.go` 和 `backend-go/internal/server/export_test.go` 提供临时库和 `httptest` 示例，分别验证旧视图的缺省字段与部分更新，以及 ZIP 字节、Unicode 路径、凭证防重放、路径穿越和草稿范围隔离。可用 `git show 82fe1df:backend-go/internal/server/export_test.go` 查看实现。

| 修改范围 | 核对与回归 |
| --- | --- |
| API 或响应字段 | 对照 `server.go` 注册位置、处理器、DTO 和前端 API。保持状态码、空数组/空对象、204 和文件内容类型语义。用 `httptest` 经 `s.Router` 验证，以覆盖路由和库身份校验。 |
| 上传、覆盖、删除 | 使用同名文件分别验证三种策略，混入无效图片检查 201 下的 `failed`。核对行、原图、两档缩略图、旧封面与 FTS，切库后用旧身份验证 409。 |
| 数据库或图集偏好 | 用空库和旧库分别打开，检查默认值和外键。并发修改同一图集的不同视图字段或颜色规则，核对单次失败是否完整回滚。新增表或字段时考虑旧库的明确迁移步骤。 |
| 元数据 | 用带 PNG 文本和 WebP EXIF 的样图验证，再测坏 CRC、丢失原图、子图、绕过节点、多采样阶段和大种子。刷新后核对列表、详情和导出提示词。 |
| 导出 | 先准备路径，再下载 ZIP，校验 Unicode 和重复路径、原图字节、草稿重开、过期或重放以及切库。改模板变量或路径规则时和 [前端实现](../../frontend/src/utils/batchExport.js) 一起核对。 |

最低限度的人工联调可使用第 1 节的空库。访问 `/api/settings` 和 `/api/groups`，创建图集并上传一张测试图片，打开缩略图和详情，添加标签后搜索，再执行一次批量导出并解包检查。用临时目录切库可确认图集、设置和文件隔离。前端颜色分组需要遍历整个图集，超大单图集场景应联动检查分页进展和重复项。

## 10. 馆藏统计

[statistics.go](../internal/server/statistics.go) 在一次 SQLite 查询中读取现存插画总数 `illustration_count` 和 `groups`。每个图集含 `id`、`name`、`cover_illustration_id`、`illustration_count`、`disk_bytes` 和 `days`。图集按已保存的顺序排列，其余图集按创建时间和 ID 倒序追加，空图集也会返回。

- `today` 是服务端本地日期。`days` 按 `created_at` 的日期归并并升序返回 `{date,count}`，包含公元 1 年至 `today` 期间有记录的日期。缺少有效日期或超出该范围的记录仍计入当前总量。删除与覆盖会移除旧记录，逐日导入和累计趋势描述目前仍在库的插画。
- `database_bytes` 汇总 `database_files` 下的 `main_bytes`、`wal_bytes` 和 `shm_bytes`。缺少的 WAL 或 SHM 文件计为零。`storage.uploads_bytes` 和 `storage.models_bytes` 分别统计当前库 `uploads` 和 `models` 下的普通文件，包含缩略图、暂存及残留文件，跳过符号链接。图集的 `disk_bytes` 从同次上传目录扫描提取，统计 `uploads/<groupId>` 下的普通文件。SQLite 查询与文件扫描分别取样。
- `storage.basis` 为 `allocated` 时，所有磁盘分项均使用文件系统报告的分配字节，包含 Windows、Linux 和 macOS。其余平台使用文件长度并返回 `file_length`。该汇总以文件为单位，共享磁盘块随各自文件计入。
- `GET /statistics/groups/{groupId}/storage` 返回 `{illustrations: {"<id>": <bytes>}}`。每张插画计入当前记录对应的原图和两档缩略图，缺失或无法安全定位的文件计为零。颜色组由前端读取 `GET /group-config` 和 `GET /export/catalog?scope=<groupId>` 确定成员，再汇总这些成员的磁盘占用。多个方案可分别统计同一批插画。与插画记录无关联的暂存和残留文件只计入图集及馆藏总量。
